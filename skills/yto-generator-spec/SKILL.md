# 功能规格生成器

## 强制规范
- 遵循 always-on.md 全局规则
- 禁止读取本步骤指定规范文档之外的任何文件
- 严禁自行推导用户未提及的业务细节
- 严禁写入技术实现方案（类名、接口路径、框架、数据库）

### 任务拆解强制规则

**在生成待办任务列表（Todo）时，必须严格遵循以下规则：**

1. **每个步骤必须作为独立的一条待办任务**，共 5 条，不得合并、不得省略
2. **每条待办必须包含完整的步骤名称**：
   - `步骤 1: 提取业务需求 — 解析需求来源`
   - `步骤 2: 区分触发模式 — 工作流触发或用户触发`
   - `步骤 3: 读取业务地图 — 读取 .spec/oc-project-business-map.md`
   - `步骤 4: 生成 spec.md — 生成结构化功能规格文档`
   - `步骤 5: 阻塞等待用户确认 — 确认无误后继续`
3. **每个步骤必须独立完成后才能标记为完成**

---

## 所需参数

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| businessDemand | String | 是 | 用户业务需求描述 |

## 执行流程

### 步骤1：提取业务需求
- 检查 `businessDemand` 的值：
  - 若为文件路径，读取该文件内容作为业务需求
  - 若为文本字符串，直接作为业务需求
- 输出：✅ 步骤1完成  

### 步骤2：区分触发模式
- 被其他 Skill 的 执行步骤触发：参数缺失则直接终止并提示缺失字段
- 用户直接触发：参数不全则提示用户输入
- 输出：✅ 步骤2完成

### 步骤3：读取业务地图-`.spec/oc-project-business-map.md`
- 输出：✅ 步骤3完成

### 步骤4：生成 spec.md，必须包含必要内容，严禁自行推导用户未提及的业务细节，严禁写入技术实现方案
- 保存至当前需求目录下 spec.md 文件中
- 必要内容：
  - **上下文摘要**（业务背景、目标用户、核心问题）
  - **用户故事与验收标准**（Given-When-Then 格式）
  - **功能需求列表**（FR-XXX）
  - **业务实体与数据边界**（用自然语言描述核心业务概念及其关系，不定义表结构或类名）
  - **非功能需求**（仅当需求中明确提及量化指标时才写，不自行推测）
  - **范围外声明**（明确本次需求不包含的内容，避免需求蔓延）
- 输出：✅ 步骤4完成

### 步骤5：阻塞等待用户确认，必须暂停执行，必须获得确认
- 提示用户："请检查以上功能规格，确认无误后回复'确认'继续，或提出修改意见。"
- 用户回复"确认"→ 继续
- 用户提出修改 → 修改后重新等待确认

## spec.md 输出格式模板

```markdown
# 功能规格说明书: {需求名称}

## 1. 上下文摘要

### 业务背景
{描述业务背景和核心问题}

### 目标用户
{描述目标用户群体}

## 2. 用户故事与验收标准

### US-001: {用户故事标题}
**作为** {角色}，**我希望** {功能}，**以便** {价值}

**验收标准：**
- **AC-001**: Given {前置条件}, When {操作}, Then {预期结果}
- **AC-002**: Given {前置条件}, When {操作}, Then {预期结果}

## 3. 功能需求列表

| 编号 | 功能需求 | 优先级 | 关联用户故事 |
|------|---------|--------|-------------|
| FR-001 | {功能描述} | 高/中/低 | US-001 |

## 4. 业务实体与数据边界

{用自然语言描述核心业务概念及其关系}

## 5. 非功能需求

{仅当需求中明确提及量化指标时才写}

## 6. 范围外声明

- 本次需求不包含：{排除项}
```

## 输出格式
- 输出 `spec.md` 文件路径
- 提示用户：“请检查以上功能规格，确认无误后回复‘确认’继续，或提出修改意见。”
