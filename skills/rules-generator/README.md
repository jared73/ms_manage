# rules-generator 使用说明

> 给你（团队成员）30 秒看懂这个 skill 怎么用。

## 一句话说明

**输入一个项目，输出一套专属的 rule 文件。**

## 我什么时候该用它？

- ✅ 我接手了一个**新项目**，要给项目配 SDD
- ✅ 我要给**老项目**配 SDD（从代码反推）
- ✅ 我们**推广 SDD 到兄弟项目**
- ✅ 项目业务方向变了，rule 要重新生成

## 它生成什么东西？

会生成 4 个 rule 文件，落到 `.qoder/rules/`：

```
.qoder/rules/
├── always-on.md          # 硬约束（命名、注解、包路径）
├── java-class.md         # Java 类通用规则
├── spec-reference.md     # 何时读哪份规范
└── pom-xml.md            # POM 修改规则
```

**老项目还会额外生成一份报告**：

```
.qoder/rules/
└── GENERATION-REPORT.md  # 记录扫描结果 + 每个质问的选择
```

## 怎么用？（两种方式）

### 方式 1：直接告诉 AI

```
你：帮我用 rules-generator 给这个项目配 rule
```

AI 会自动跑流程：
1. 判断项目类型（新/老）
2. 老项目会先扫描代码
3. 找不一致点，逐个质问你
4. 生成 4 个 rule 文件

### 方式 2：手动执行步骤

详见 `SKILL.md`，按 5 个步骤文件执行。

## 我需要做什么？

### 新项目
- 回答 1 个问题：**包名风格**
- 其他都用默认

### 老项目
- 回答 8 个左右的质问（每个都有推荐项）
- 大部分情况**无脑选 A** 就行

## 我应该选 A 还是 B？

**99% 的情况选 A**（推荐项）。推荐项是基于行业最佳实践 + 项目现状推断的最优解。

只有两种情况不选 A：
1. **团队有明确的其他约定**（比如公司规定必须用 @Validated）
2. **A 选项有硬伤**（比如 A 会和现有依赖冲突）

## 跑完之后呢？

1. **review 生成的 4 个 rule**——AI 可能有偏差
2. **跑 `rules-checker`**——看哪些老代码不合规
3. **跑 `code-fixer`**——批量修复
4. **新代码自动合规**——CI 会卡住不合规的 PR

## 常见问题

### Q1：跑完之后我不满意，能重跑吗？
**A**：能。直接说"用 rules-generator 重新生成"，会重新质问。

### Q2：生成的 rule 我要改，怎么办？
**A**：直接编辑 `.qoder/rules/*.md`。下次跑 rules-generator 会覆盖，建议先备份。

### Q3：项目代码一半是 Java 一半是 Python，支持吗？
**A**：当前只支持 Java 后端。Python 项目要另外适配。

### Q4：跑一次要多久？
**A**：
- 新项目：5 分钟
- 老项目（中等规模 100–500 个类）：30–60 分钟
- 老项目（大型 1000+ 类）：1–2 小时

### Q5：为什么有"质问"环节？能跳过吗？
**A**：不能跳过。质问是这个 skill 的核心价值——发现不一致、让用户决策。如果你觉得质问太多，可以告诉我"先按推荐项默认生成"，但建议**至少 review 一下推荐项是否符合预期**。

## 进阶使用

### 跳过质问（不推荐）
```
你：用 rules-generator，全部用推荐项
```
AI 会跳过质问环节，直接按推荐项生成。**风险**：如果推荐项和你团队实际不符，rule 会失真。

### 只跑扫描不生成
```
你：用 rules-generator 扫一下代码，先不生成
```
AI 会执行步骤 02 + 03，输出扫描报告，不生成 rule。

### 单独执行某个步骤
```
你：用 rules-generator 执行步骤 04 的质问
```
可以单独跑某个步骤，适合分多次完成。

## 反馈问题

如果你用的时候发现：
- 扫描漏掉了某些情况
- 质问不合理
- 生成的 rule 有错

请反馈给 skill 维护者，**附上**：
- 项目类型（新/老）
- 项目规模（多少个类）
- 具体问题描述

这些反馈会用于迭代 skill 本身。
