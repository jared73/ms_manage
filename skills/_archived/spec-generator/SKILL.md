# 产品规格文件生成技能（spec-generator）

## 触发条件

当用户输入以下格式时触发：
- `生成spec+ 需求描述`（例如：`生成spec+ 用户登录认证模块，支持账号密码和手机验证码两种方式`）
- `生成spec+` + 附件需求文档

## 前置依赖

- 用户提供的模块需求描述（至少 50 字）或附件需求文档
- 如果需求描述过于简略，需主动向用户追问补充

## 核心工作流程（标准 4 阶段 10 任务 SOP）

**任一阶段存在信息缺失、需求模糊、规则不确定问题，必须立即暂停工作并主动向用户确认，未完成确认不得进入下一阶段，严禁擅自推进、脑补需求。**

### 任务拆解强制规则（禁止合并阶段）

**在生成待办任务列表（Todo）时，必须严格遵循以下规则：**

1. **阶段 1 和阶段 3 必须拆分为独立子任务**，阶段 2、阶段 4 各自作为独立待办，共计 10 条待办任务，不得合并、不得省略
2. **每条待办必须包含完整的阶段名称和目标描述**，格式如下：
   - `阶段 1.1: 解析需求 — 从用户输入提取模块名称、英文名、核心场景、关键功能点`
   - `阶段 1.2: 确认模块信息 — 向用户确认模块中文名和英文名`
   - `阶段 1.3: 需求对齐与澄清 — 识别模糊/冲突/遗漏点，以可点击选项方式向用户确认（用户只需点击选择）`
   - `阶段 2: 创建目录结构与 README — 创建 specs/{module}/ 目录并生成索引导航文件`
   - `阶段 3.1: 生成 01-overview.spec.md — 功能规格主文件（愿景、流程、功能清单、非功能需求）`
   - `阶段 3.2: 生成 02-user-stories.md — 用户故事清单（角色驱动的业务故事）`
   - `阶段 3.3: 生成 03-state-machine.md — 验收标准（Given-When-Then 行为驱动验收）`
   - `阶段 3.4: 生成 04-edge-cases.md — 边界场景与异常矩阵`
   - `阶段 3.5: 生成 05-acceptance.md — 界面与模块状态机`
   - `阶段 4: 交付确认与验收 — 输出完成确认信息，引导用户检查`
3. **严禁出现以下合并写法**：
   - ❌ `阶段 1: 需求理解与确认（合并解析和确认）`
   - ❌ `阶段 3: 逐个生成规格文件（合并 5 个文件）`
   - ❌ `阶段 3-4: 生成文件并交付`
   - ❌ `阶段 3~4（合并执行）`
   - ❌ `后续阶段（阶段 3-4）`
4. **每条待办必须独立完成后才能标记为完成**，前一条未完成不得开始后一条
5. 阶段 3 的 5 个文件必须按顺序逐个生成，每个文件生成后告知用户进度

### 阶段 1：需求理解与确认

**目标**：全面理解用户需求，提取模块关键信息并向用户确认。

**执行步骤**：

#### 1.1 解析需求

从用户输入中提取以下关键信息：
- **模块名称**：中文名称
- **模块英文名（module key）**：用于目录命名，采用 kebab-case（如 `user-auth`）
- **核心业务场景**：用户是谁、在什么场景下、要解决什么问题
- **关键功能点**：列出主要功能

如果用户输入的需求描述过于简略（少于 50 字），必须使用 `ask_user_question` 工具向用户追问以下信息：
1. 这个模块的核心用户角色有哪些？
2. 最关键的业务场景是什么？
3. 有没有现有的需求文档或设计文档可以参考？

#### 1.2 确认模块名称

提取或推断模块英文名后，使用 `ask_user_question` 工具确认：
- 模块中文名称
- 模块英文名（用于目录和文件命名）

**只有当用户明确提供了模块名称时才可跳过此确认步骤。**

#### 1.3 需求对齐与澄清

**目标**：全面理解需求，识别关键疑问点，以**可点击选项**方式向用户确认，用户只需点击选择即可，无需手动输入。

**执行步骤**：
1. 全面核查用户提供的需求内容，主动识别以下问题：
   - 模糊描述、语义歧义
   - 逻辑冲突、规则缺失
   - 场景遗漏、边界不清
   - 状态流转不完整
2. 对每个疑问点，**主动分析并预设 2~4 个合理选项**，每个选项包含简洁的标签和描述
3. 使用 `ask_user_question` 工具一次性发起确认，用户只需点击选择：
   - 每次调用最多包含 **8 个问题**，每个问题提供 **2~4 个选项**
   - 如果疑问点超过 6 个，按优先级分批发起，但**最多不超过 2 批**
   - 每个选项必须有明确的 `label`（简短标签，1~5 个词）和 `description`（选项含义和影响）
4. **选项设计示例**：
   - 疑问：「应用禁用后是否允许查看历史数据？」
     - 选项 A：`label: "允许查看"` / `description: "禁用后用户只能查看历史数据，不能进行新操作"`
     - 选项 B：`label: "完全禁止"` / `description: "禁用后所有功能均不可访问，包括历史数据"`
     - 选项 C：`label: "仅管理员可查看"` / `description: "普通用户禁止访问，管理员角色可查看历史数据"`
   - 疑问：「应用名称是否允许重复？」
     - 选项 A：`label: "不允许重复"` / `description: "全局唯一校验，创建时若名称已存在则拒绝"`
     - 选项 B：`label: "允许重复"` / `description: "不做唯一性校验，不同应用可以同名"`
5. 用户选择后，直接采用选择结果作为正式需求，无需额外确认

**澄清规则（防止无限循环）**：
- **最多澄清 1 轮**（最多 2 批提问）：所有疑问点一次性以选项形式提出，用户选择后无论是否全部解答，都进入下一阶段
- 用户未选择的阻断级疑问：采用第一个选项（默认推荐）作为合理假设，在后续文件中标注"假设"
- 用户未选择的非阻断级疑问：直接采用第一个选项，在后续文件中标注"假设"
- **严禁反复追问**：不得因用户未回答某个问题而重复提问或拒绝推进
- 需求中已明确描述的内容，直接采用，不需要再向用户确认

### 阶段 2：创建目录结构与 README.md

**目标**：创建标准化的目录结构并生成索引导航文件。

#### 2.1 创建目录

在项目根目录下创建以下目录结构：

```
specs/
└── {module}/
```

如果 `specs/` 目录已存在，则在其中创建 `{module}` 子目录。

#### 2.2 编写 README.md

在 `specs/{module}/README.md` 中写入以下内容：

```markdown
# {模块中文名称} - 产品规格文档

> 模块标识: {module_name} | 版本: V1.0.0 | 创建日期: {当前日期}

## 📂 文档索引

| 序号 | 文件名 | 说明 |
| --- | --- | --- |
| 1 | [01-overview.spec.md](./01-overview.spec.md) | 功能规格主文件 - 愿景、流程、功能清单、非功能需求 |
| 2 | [02-user-stories.md](./02-user-stories.md) | 用户故事清单 - 角色驱动的业务故事 |
| 3 | [03-state-machine.md](./03-state-machine.md) | 验收标准 - Given-When-Then 行为驱动验收 |
| 4 | [04-edge-cases.md](./04-edge-cases.md) | 边界场景与异常矩阵 - 异常处理机制 |
| 5 | [05-acceptance.md](./05-acceptance.md) | 界面与模块状态机 - 状态流转图 |

## 🔄 文档变更记录

## 📋 快速导航

- **看用户视角** → [02-user-stories.md](./02-user-stories.md)
- **看验收标准** → [03-state-machine.md](./03-state-machine.md)
```

### 阶段 3：逐个生成规格文件

**目标**：按顺序生成 5 个规格文件，每个文件独立生成并告知用户进度。

**按照以下顺序，逐个生成 5 个规格文件。每个文件生成后，告知用户进度。**

#### 3.1 生成 `01-overview.spec.md`

严格遵循以下模板，根据需求内容填充所有 `{占位符}`：

```markdown
# 功能规格书 (Feature Specification): {模块英文名称}

## 1. 基础信息 (Metadata)
- **模块名称**: {例如：用户认证中心 / 订单管理}
- **标识符 (Module Key)**: {module_name}
- **版本号**: V1.0.0
- **全权负责人**: [产品经理姓名]
- **生效日期**: {当前日期}

## 2. 功能愿景与核心目标 (Vision & Goal)
- **业务痛点**: {描述用户在什么场景下遇到了什么困难}
- **核心目标**: {通过本功能解决什么问题，预期的核心业务指标是什么}

## 3. 核心业务流程 (Core Business Process)

\`\`\`mermaid
graph TD
    A[用户触发] --> B{是否满足条件?}
    B -- Yes --> C[执行核心逻辑]
    B -- No  --> D[抛出异常/提示]
    C --> E[更新数据并结束]
\`\`\`

## 4. 核心功能需求清单 (Functional Requirements)

| 需求ID | 子功能名称 | 描述 | 涉及角色 | 优先级 (P0/P1) |
| --- | --- | --- | --- | --- |
| REQ-001 | {示例功能} | {当用户点击...时，系统应当...} | {角色} | P0 |

## 5. 非功能性需求 (Non-Functional Requirements)

* **性能**: 核心 API 响应时间 $< 200\\text{ms}$，支持并发 QPS $> 1000$。
* **安全性**: {根据模块特点填写安全需求}
* **国际化**: 支持中英双语，文案从 `i18n` 资源包读取。
```

**关键要求**：
- Mermaid 流程图必须准确反映核心业务逻辑，不得使用通用的示例流程
- 功能需求清单至少包含 3 条，按优先级 P0 > P1 排序
- 非功能性需求需根据模块特点定制，不能简单复制模板

#### 3.2 生成 `02-user-stories.md`

严格遵循以下模板：

```markdown
# 用户故事清单 (User Stories): {模块英文名称}

> 💡 格式标准：作为 [某种角色], 我想 [做某件事], 以便 [获得什么业务价值]。

## [US-01] {故事主题一}
- **故事描述**: 作为 **[角色]**, 我想 **[执行的操作]**, 以便 **[达到的目的]**。
- **业务场景示例**: {例如：小张作为运营，希望一键导出报表，不用再手动复制}
- **关联需求ID**: REQ-001

## [US-02] {故事主题二}
- **故事描述**: 作为 **[角色]**, 我想 **[执行的操作]**, 以便 **[达到的目的]**
- **关联需求ID**: REQ-002
```

**关键要求**：
- 每个用户角色至少有 1 条故事
- 故事总数不少于 3 条
- 每条故事必须关联到 01-overview 中的需求 ID
- 业务场景示例必须具体、可感知，不能写空话

#### 3.3 生成 `03-state-machine.md`

严格遵循以下模板：

```markdown
# 验收标准 (Acceptance Criteria): {模块英文名称}

> 💡 格式标准：严格采用 Given-When-Then (GWT) 自动化测试行为驱动语法。

## [AC-001] {功能点 A 的成功场景验收}
- **场景描述**: {用户在提供正确完整信息时，操作成功}
- **验收步骤**:
  - **Given (前提条件)**: {具体的前置条件，包含数据和状态}
  - **When (触发动作)**: {具体的用户操作}
  - **Then (预期结果)**: {具体的系统响应和数据变更}

## [AC-002] {功能点 A 的失败场景验收 (数据校验)}
- **场景描述**: {用户输入非法数据时，系统拦截并友好提示}
- **验收步骤**:
  - **Given (前提条件)**: {具体的前置条件}
  - **When (触发动作)**: {具体的非法操作}
  - **Then (预期结果)**: {具体的错误提示和系统行为}
```

**关键要求**：
- 每个核心功能至少有 1 条成功场景 + 1 条失败场景
- Given 中必须包含具体的数据值（如金额、数量、状态码），不能用模糊描述
- Then 中必须包含可验证的断言（如"数据库插入一条状态为 PENDING 的记录"）
- 至少包含 3 组验收标准（AC-001 ~ AC-003）

#### 3.4 生成 `04-edge-cases.md`

严格遵循以下模板：

```markdown
# 边界场景与异常矩阵 (Edge Cases): {模块英文名称}

## 1. 基础设施与网络级异常 (Infrastructure Failures)
- **[EC-001] 网络抖动/断网**: 
  - *处理机制*: 前端请求超时设定为 5s，超时后触发全局 Toast 提示"网络连接繁忙，请稍后再试"，严禁页面崩溃或无限 Loading。
- **[EC-002] 服务端 500/502 错误**:
  - *处理机制*: 降级路由到统一的 Error Page，并提供"重试"按钮。

## 2. 业务边界与并发异常 (Business Edge Cases)
- **[EC-003] 表单重复提交 (防重)**:
  - *处理机制*: 用户点击提交后，前端按钮立刻进入 `loading` + `disabled` 状态；后端基于 `Token/Idempotent-Key` 实现分布式幂等锁，锁定时长 3s。
- **[EC-004] 极值与大数据量注入**:
  - *处理机制*: 输入框限制最大字符长度 255，防止超长文本撑破 UI 布局或导致 SQL 溢出。
```

**关键要求**：
- 基础设施异常至少 2 条
- 业务边界异常至少 2 条，且必须包含防重复提交
- 每条异常处理机制必须明确：前端做什么、后端做什么、用户看到什么
- 根据模块特点补充特定的边界场景（如金额类模块需要考虑负数/零值/超大值）

#### 3.5 生成 `05-acceptance.md`

严格遵循以下模板：

```markdown
# 界面与模块状态机 (Status Matrix): {模块英文名称}

## 1. 全局状态流转图 (Statechart)

\`\`\`mermaid
stateDiagram-v2
    [*] --> Init: 页面加载
    Init --> Loading: 发起异步请求
    Loading --> Success: 数据返回且不为空
    Loading --> Empty: 数据返回但无记录
    Loading --> Error: 请求失败/超时
    Success --> Loading: 触发刷新/翻页
    Empty --> Loading: 点击重新加载
    Error --> Loading: 点击重试
\`\`\`

## 2. 核心实体状态流转

\`\`\`mermaid
stateDiagram-v2
    [*] --> {初始状态}: {触发条件}
    {状态A} --> {状态B}: {动作/事件}
    {状态B} --> {状态C}: {动作/事件}
\`\`\`
```

**关键要求**：
- 全局状态流转图必须包含：Init、Loading、Success、Empty、Error 五个状态
- 核心实体状态流转图必须根据模块业务特点绘制（如订单：待支付 → 已支付 → 已发货 → 已完成）
- 状态流转必须与 01-overview 中的业务流程一致
- 每个状态转换必须标注触发条件/动作

## 重要约束

1. **阶段禁止合并**：必须严格按 10 条待办任务拆分，阶段 1 拆为 1.1/1.2/1.3，阶段 3 拆为 3.1~3.5，严禁合并，每条必须独立创建、独立执行、独立标记完成
2. **文件内容不能是空模板**：所有 `{占位符}` 必须根据用户输入的需求内容填充，生成有实际意义的规格内容
3. **Mermaid 图必须准确**：流程图和状态图必须反映实际业务逻辑，不能使用通用的占位示例
4. **关联性必须一致**：用户故事中的 REQ-ID、验收标准中的 REQ-ID、功能需求清单中的 REQ-ID 必须一致
5. **逐步生成**：5 个规格文件按顺序逐个生成，每生成一个就告知用户进度
6. **日期使用当前日期**：所有文件中的日期使用当前系统日期
7. **模块名规范**：英文模块名使用 kebab-case（小写字母+连字符），如 `user-auth`、`order-management`
8. **需求澄清高效推进**：最多澄清 1 轮，一次性列出所有疑问，用户回复后无论是否全部解答都必须进入下一阶段，严禁反复追问
9. **主动推进对齐**：发现需求问题立即提出，不延后、不隐瞒
10. **全程中文**：所有沟通和输出均使用中文

## 行为约束
