# 03 · 模式推断

> 目标：从材料收集中识别"模糊/缺失/不一致"点，作为质问的依据。
>
> **本步骤不质问用户，只识别问题。**质问在步骤 04。

## 推断逻辑

context 的"模糊"和 rules 的"不一致"是**不同的概念**：

| 维度 | rules-generator | context-generator |
|------|----------------|-------------------|
| 问题类型 | 不一致（多种实现） | 模糊（信息缺失/冲突） |
| 识别方法 | 统计占比 | 检查覆盖率 |
| 质问类型 | 选择题（选 A/B/C） | 填空题 + 选择题（"是什么"） |

## 模糊度评估标准

| 模糊度 | 判定 | 处理 |
|--------|------|------|
| **0–20%** | 信息充分 | ✅ 直接生成 |
| **20–50%** | 部分缺失 | ⚠️ 质问，列出推断 |
| **50–80%** | 大量缺失 | ⚠️ 必须质问 |
| **> 80%** | 几乎无信息 | ⚠️ 强烈推荐新项目路径 |

## 推断流程

### 步骤 3.1：建立"待质问清单"

把材料收集中所有"模糊/缺失/冲突"汇总：

```markdown
## 待质问清单

| # | 维度 | 模糊程度 | 优先级 |
|---|------|---------|--------|
| 1 | 项目一句话定位 | README 无 | 高 |
| 2 | 产品线划分 | pom 推断 lms/oc/cmd | 中 |
| 3 | 核心模块清单 | 推断 3 个 | 高 |
| 4 | 业务术语 | README 散落 5 个 | 中 |
| 5 | 团队成员 | 完全缺失 | 低 |
| 6 | 业务指标 | 完全缺失 | 中 |
| 7 | 架构类型 | 微服务（推断） | 低 |
| 8 | 部署方式 | 完全缺失 | 低 |
```

### 步骤 3.2：分析每个"模糊点"

对每个模糊点，输出**完整分析**（示例）：

```markdown
### 模糊点 1：产品线划分

**现有证据**：
- pom.xml 模块名：`oc-order-api`、`oc-order-service`、`lms-access-default-api`
- README.md 提到"订单系统"和"平台接入"
- 业务文档路径：未发现

**推断**：
- 至少存在 2 条产品线：OC（订单中心）、LMS（物流/平台接入）
- 可能还有第 3 条（CMD？）

**质询点**：项目有几条产品线？分别是什么？

**该问题将作为质问 1/6 在步骤 04 提出**
```

### 步骤 3.3：判断是否需要质问

每个模糊点都要回答 3 个问题：

```
Q1：现有证据能否 100% 确定答案？
  - 是 → 直接采用
  - 否 → 必须质询

Q2：质询能否由用户轻松回答？
  - 是 → 加入质问清单
  - 否 → 标注"待团队讨论"

Q3：答案错误是否会导致后续生成失败？
  - 是 → 优先级高
  - 否 → 优先级低
```

### 步骤 3.4：生成"质问清单"

把"需要质问"的模糊点按优先级排好：

```markdown
## 质问清单（步骤 04 将依次执行）

| # | 主题 | 优先级 | 证据 | 期望用户操作 |
|---|------|--------|------|------------|
| 1 | 产品线划分 | 高 | pom 推断 2 条 | 确认/补充 |
| 2 | 项目一句话定位 | 高 | README 无 | 填空 |
| 3 | 核心模块清单 | 高 | pom 推断 | 确认/补充 |
| 4 | 业务术语 | 中 | README 散落 | 补充 |
| 5 | 业务指标 | 中 | 无 | 填空 |
| 6 | 团队/联系人 | 低 | 无 | 填空 |
```

**最大质问数：6 个**（context 比 rules 更少，3–6 个为佳）

**最少质问数：1 个**（避免无意义质问）

## 6 个常见模糊点模板

### 模板 1：产品线划分

**收集证据**：
```bash
# 从 pom.xml 推断产品线
grep "<artifactId>" pom.xml | grep -oE "^[a-z]+-" | sort -u

# 从代码包路径推断
find src -name "*.java" | head -5 | xargs -I {} dirname {} | sort -u
```

**质问模板**：见 `questions/01-product-line.md`

### 模板 2：项目一句话定位

**收集证据**：
- README.md 是否有"项目简介"章节
- 是否有"这是什么"的描述

**质问模板**：见 `questions/02-project-tagline.md`

### 模板 3：核心模块清单

**收集证据**：
```bash
# 从 pom.xml 推断模块
grep "<artifactId>" pom.xml

# 从 Application 类推断
find . -name "*Application.java"
```

**质问模板**：见 `questions/03-core-modules.md`

### 模板 4：技术架构

**收集证据**：
- 架构图
- 模块数量（多=微服务，单=单体）
- 是否有 API 网关

**质问模板**：见 `questions/04-architecture.md`

### 模板 5：业务术语

**收集证据**：
- README 中的缩写
- pom.xml 中的产品线代号
- 文档中的业务名词

**质问模板**：见 `questions/05-glossary.md`

### 模板 6：项目成熟度

**收集证据**：
```bash
# Git 提交数
git log --oneline | wc -l

# 项目运行时间
git log --reverse --format="%ai" | head -1
```

**质问模板**：见 `questions/06-maturity.md`

```markdown
# 模式推断报告

**将质问数**：{K} 个

## 充分项（直接采用）

✅ 技术栈：{从 pom.xml 推断}
✅ 包路径：{从代码推断，100%}

## 模糊项（将进入步骤 04 质问）

⚠️ 产品线划分（材料推断 2 条）
⚠️ 项目一句话定位（无明确描述）
⚠️ 核心模块清单（pom 显示 4 个）
⚠️ 业务术语（README 散落 5 个）
⚠️ 业务指标（无）
⚠️ 团队/联系人（无）

---

## 质问计划

将依次询问 6 个问题。

预计用户操作：
- 6 个问题 × 1 分钟 ≈ 6 分钟
- 部分可批量回答

进入步骤 04-ask-questions.md。
```

## 注意事项

1. **不读代码**——只看文档推断
2. **模糊的写模糊**——不要把推断当事实
3. **要给证据**——每个推断都列出来源
4. **优先级要标**——让用户知道哪些必答
5. **限制在 6 个以内**——超过会让用户疲劳
6. **填空题和选择题并存**——context 比 rules 更需要填空

## 与 rules-generator 的对比

| 维度 | rules-generator 推断 | context-generator 推断 |
|------|--------------------|---------------------|
| 关注点 | 不一致的实现方式 | 缺失/模糊的信息 |
| 证据类型 | grep 统计 | 文档摘要 |
| 质问类型 | 选择题为主 | 填空题 + 选择题 |
| 数量 | 8 个左右 | 6 个左右 |
| 输出 | 4 个 rule | 6 个 context |
