# 04 · 质问用户

> 目标：按推断清单，依次向用户提出问题，收集项目背景信息。
>
> **这是整个 skill 的核心价值**——发现信息缺失，主动质询用户补充。

## 质问原则

### 原则 1：填空题 + 选择题并存
context 的质问比 rules 更"开放"——很多问题需要用户**主动描述**而不是**选择**。

```markdown
# rules 质问（选择题为主）
"Controller @Valid 用哪种？"
A. @Valid
B. 无校验

# context 质问（填空题为主）
"请用一句话描述项目是做什么的："
（用户自由输入）
```

### 原则 2：给证据 + 推断
不要让用户"凭空回答"，要给"基于现有材料的推断"。

```markdown
## 质问 1/6：产品线划分

**现有证据**：
- pom.xml 包含 `oc-*` 和 `lms-*` 模块
- README 提到"订单中心"和"物流接入"
- 推测：至少有 2 条产品线

**请确认**：
- 上面推断对吗？
- 实际有几条产品线？分别是什么？
- 有没有第 3 条（如 cmd）？
```

### 原则 3：填空题也要给选项
填空题不应该是完全开放的"自由输入"，要**给常见答案做参考**。

```markdown
## 质问 2/6：项目一句话定位

**请用一句话描述项目**（30 字以内）：

参考选项（可直接选 A/B/C/D 或自行输入）：
A. 圆通订单中心，处理订单全生命周期
B. 平台接入层，对接拼多多/微信/支付宝
C. 订单推送平台，向各渠道推送订单
D. 其他：______
```

### 原则 4：批量回答友好
context 的质问**更适合批量回答**：

```markdown
# 用户可以一次性回答所有问题
1. 产品线：oc, lms, cmd
2. 定位：圆通订单处理中心
3. 核心模块：order, payment, inventory
4. 架构：微服务
5. 术语：LMS=物流, OC=订单中心, CMD=推送
6. 阶段：稳定期
```

### 原则 5：限制总数
context 质问**最多 6 个**——多了用户会烦。

## 质问执行流程

### 步骤 4.1：准备工作

```markdown
# 准备开始质问

项目共发现 {N} 个模糊点，将依次询问 {M} 个问题。

预计耗时：{M} × 1 分钟 ≈ {X} 分钟

大部分问题是填空题，请准备好项目元信息。
也可以批量回答，例如：
1. oc, lms, cmd
2. 圆通订单处理中心
3. order, payment, inventory
4. 微服务
5. LMS=物流, OC=订单中心
6. 稳定期

按 Enter 开始第一个问题。
```

### 步骤 4.2：依次质问

每问完一个问题，AI 要：
1. **确认用户回答**
2. **复述一遍**（避免理解错误）
3. **简短总结**（"好，我们有 3 条产品线"）
4. **进入下一个问题**

```markdown
✅ 收到：3 条产品线（oc、lms、cmd）

进入质问 2/6：项目一句话定位
```

### 步骤 4.3：批量回答模式

```markdown
你：1. 3 条产品线（oc, lms, cmd）
   2. 圆通订单处理中心
   3. order, payment, inventory
   4. 微服务
   5. LMS=物流, OC=订单中心, CMD=推送
   6. 稳定期

AI：（批量记录 6 个回答）
   ✅ 6 个问题全部回答，进入步骤 05
```

### 步骤 4.4：收尾

```markdown
# 质问完成

## 用户回答汇总

| # | 主题 | 回答 | 备注 |
|---|------|------|------|
| 1 | 产品线 | oc, lms, cmd | 3 条 |
| 2 | 项目定位 | 圆通订单处理中心 | |
| 3 | 核心模块 | order, payment, inventory | |
| 4 | 技术架构 | 微服务 | |
| 5 | 业务术语 | LMS=物流, OC=订单中心, CMD=推送 | |
| 6 | 项目成熟度 | 稳定期 | |

---

下一步：进入步骤 05-generate-context.md，生成 6 个 context 文件。
```

## 特殊场景处理

### 场景 1：用户回答"全部默认"

```markdown
你：按你推断的默认填吧
AI：好的，已记录所有答案为推荐项/推断值。
   ⚠️ 注意：context 比 rules 更需要人工确认，
   默认值可能不准确，建议 review。
```

### 场景 2：用户回答"先不生成，看报告"

```markdown
你：先不生成，给我看收集的材料
AI：（输出材料收集报告 + 模式推断报告，暂停）
```

### 场景 3：用户对某个问题犹豫

```markdown
你：这个我看不出来，能给更多上下文吗？
AI：（提供该问题相关的证据 + 常见选项分析）
```

### 场景 4：项目太小，几乎无材料

```markdown
AI：项目材料不足（< 3 份文档），将按行业最佳实践生成，
   您可以选择确认或修改。
```

### 场景 5：用户提供的回答不规范

```markdown
你：产品线有 oc, lms, cmd
AI：好的，已记录：3 条产品线（oc、lms、cmd）
   注：会生成 business-map-{productLine}.md 共 3 份。
```

## 质问记录格式

每问完一个问题，AI 内部维护：

```yaml
# 内部记录（步骤 05 会用）
user_answers:
  product_lines: ["oc", "lms", "cmd"]
  project_tagline: "圆通订单处理中心"
  core_modules: ["order", "payment", "inventory"]
  architecture: "微服务"
  glossary:
    LMS: "物流管理系统"
    OC: "订单中心"
    CMD: "推送平台"
  maturity: "稳定期"

notes: {}
```

**步骤 05-generate-context.md 会读这份记录**。

## 与 rules-generator 的差异

| 维度 | rules-generator 质问 | context-generator 质问 |
|------|-------------------|---------------------|
| 题型 | 选择题为主 | 填空题 + 选择题 |
| 数量 | 8 个左右 | 6 个左右 |
| 模糊性 | 低（基于数据） | 高（基于材料） |
| 批量友好 | 一般 | 强（可一次性回答） |
| 跳过风险 | 低（有推荐项） | 高（填空题答不出） |

## 反模式（要避免）

### ❌ 反模式 1：填空题不给选项
```
请描述项目是做什么的。
（用户完全自由输入，质量参差）
```

### ❌ 反模式 2：质问超过 6 个
```
还有 10 个问题...  ← 错误
```

### ❌ 反模式 3：不给证据
```
你们有几条产品线？
（用户不知道为什么问）
```

### ❌ 反模式 4：跳过质问直接生成
```
AI：默认按微服务 + Java + Spring Boot 生成。
（没有质询，可能严重偏离）
```

```markdown
## 步骤 04 完成

**待生成文件**：6 个 context
**生成报告**：1 份

进入步骤 05-generate-context.md。
```
